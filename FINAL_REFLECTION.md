# Final Reflection

## Real-Time Systems

At the beginning of this course, I knew some basic embedded programming concepts from previous classes, but I had very little experience building complete real-time systems. Throughout the semester, I learned that designing a real-time application involves much more than just writing code that works. It requires thinking about timing, synchronization, communication between tasks, and making sure the system behaves correctly even when something goes wrong.

One of the biggest things I learned was how to choose the correct FreeRTOS synchronization primitive for different situations. Before this course, I did not fully understand why there were so many different options like queues, event groups, semaphores, mutexes, and direct task notifications. After completing the applications and the final project, I now understand that each primitive is designed for a specific purpose. For example, queues work well for transferring data between tasks, event groups allow multiple conditions to be synchronized, mutexes protect shared resources, and direct task notifications provide very fast communication between an ISR and a task. Choosing the correct primitive can improve both the performance and reliability of a system.

Another important lesson was learning how to think about system timing instead of just functionality. Measuring worst-case execution time (WCET), comparing notification latency with semaphore latency, and monitoring task heartbeats showed me that a system can appear to work correctly while still having timing problems. I also learned why separating monitoring tasks from real-time tasks on different processor cores helps reduce interference and makes the system easier to analyze.

The final project allowed me to combine everything from the previous applications into one complete system. My ThemePark Ride Safety and Dispatch Controller simulates a ride control system that processes sensor information, evaluates safety conditions, coordinates multiple tasks, responds to emergency-stop events, and detects software faults using a watchdog. Building this project helped me understand how multiple synchronization primitives work together instead of treating them as separate examples. It also reinforced the importance of designing systems that fail safely when unexpected conditions occur.

One part of the project that I found challenging was implementing and testing the fault injection behavior. Intentionally causing the Safety Controller to stall and then verifying that the watchdog detected the problem took several rounds of testing. At first, it was difficult to determine whether the behavior I observed was caused by my code or by the fault itself. After debugging the application and watching the system transition into the FAULT state, I gained a much better understanding of how monitoring and fault detection work in real-time systems.

If I continued working on this project, I would expand it by supporting multiple rides running simultaneously, storing ride events in non-volatile memory, adding additional simulated sensors, and creating a more advanced web dashboard with historical timing graphs and system statistics. These improvements would make the project more realistic and closer to an industrial embedded monitoring system.

Overall, this course gave me a much better understanding of real-time operating systems and embedded software development. I now have experience using FreeRTOS to build multitasking applications, selecting synchronization primitives, handling interrupts, measuring system performance, and designing systems that can detect and respond to failures. These are skills that I believe will be valuable in future embedded software and control systems projects, especially since I have already seen similar concepts during my SCADA internship. Looking back at where I started, I feel much more confident designing and debugging real-time embedded applications than I did at the beginning of the semester.
